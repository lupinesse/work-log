## Test-only exports

Two symbols are exported (and re-exported by the `pure-fns.js` barrel) but
are never referenced by any of the ~47 concatenated non-leaf application
source files. They are, however, imported directly by unit tests, which is
why the export clause has value. Both were introduced in the September 2026
QA refactor that split `pure-fns-export.js` into themed sub-modules.

| File | Symbol | Type | App references (excl. declaration + barrel) | Test reference |
|---|---|---|---|---|
| `src/js/pure-fns-weeklyreport.js` | `WEEKLY_REPORT_NO_TICKET_KEY` | const | 0 | `test/unit/pure-fns-weeklyreport.test.mjs` |
| `src/js/pure-fns-backup.js` | `applyBackupRetention` | function | 0 | `test/unit/pure-fns-backup.test.mjs` |

### Details

**`WEEKLY_REPORT_NO_TICKET_KEY`**

Declared in `pure-fns-weeklyreport.js` as a sentinel string
(`'__no_ticket__'`) used four times internally by `buildWeeklyTicketSummary`
to bucket entries that carry no parseable Jira ticket prefix. The constant is
correctly self-contained within its sub-module; the calling non-leaf file
(`12d-weeklyreport.js`) uses only `buildWeeklyTicketSummary` and
`formatWeeklyTicketSummaryText` from the barrel — never the sentinel directly.
The barrel (`pure-fns.js`) re-exports it, causing `script.js` to pull it in
at build time, but no concatenated non-leaf code ever references the name.

**`applyBackupRetention`**

Declared in `pure-fns-backup.js`. It is called once internally by
`buildBackupPayload` (same file, line 100) which trims multiple state arrays
through it. The only external consumer of the exported function is the unit
test suite; the calling non-leaf file (`05a-export.js`) calls
`buildBackupPayload`, not `applyBackupRetention` directly. The export is
therefore useful for isolated testing of the retention logic but is not
consumed by the app.

### Recommendation

Both exports are harmless in their current form — the barrel mechanism means
they are imported automatically and add negligible bundle overhead. However,
keeping them exported does set a precedent for exporting internal helpers
"just in case." If the team prefers to keep the public surface of each
sub-module minimal, both could be de-exported (made private) and tested
indirectly through their public wrapper (`buildWeeklyTicketSummary` and
`buildBackupPayload` respectively). That would require updating the test files
to remove the direct import of these two symbols. Not a blocking finding.

## Methodology notes

- **Analysis date:** 2026-09-14
- **Scope:** `src/js/*.js` (62 files) + `build.js` + `build-portable.js` +
  `build-config.js` + `smoke-tests.cjs` + `test/unit/*.test.mjs` (36 test
  files). This repo has no `test/unit.cjs` file — tests live under
  `test/unit/*.test.mjs`.

- **Leaf module count increased since 2026-09-11.** The September 2026 QA
  refactor split the original single `pure-fns-export.js` into eight
  sub-modules: `pure-fns-backup.js`, `pure-fns-epics.js`,
  `pure-fns-export.js`, `pure-fns-gapreport.js`, `pure-fns-rollingsummary.js`,
  `pure-fns-tasks.js`, `pure-fns-validate.js`, and `pure-fns-weeklyreport.js`.
  Combined with the pre-existing leaf modules (`app-constants.js`,
  `logger.js`, `12b-changelog-data.js`, `date-labels.js`, `signifiers.js`,
  `pure-fns.js`), the total is now 15 leaf modules (up from 11 on
  2026-09-11). The two test-only exports above are a direct result of that
  split — previously all pure-fns sub-modules were internal and not exported.

- **Build architecture.** Only the 15 LEAF_MODULES in `build-config.js` use
  `export` statements. `build.js` auto-generates an `import { ... }` line for
  every named export in each leaf (excluding `pure-fns-*.js` sub-modules,
  which surface through the `pure-fns.js` barrel instead). The remaining ~47
  source files have no `import`/`export` syntax — they are concatenated
  alphabetically into one global-scope module. "Used" therefore means the
  identifier is referenced by name in any non-leaf source file or test file,
  not just "appears in an import statement."

- **`pure-fns.js` barrel re-exports don't count as usage.** Every symbol in
  the eight `pure-fns-*.js` sub-modules is re-exported by `pure-fns.js` via
  `export { ... } from '...'`. Those barrel lines were excluded when counting
  real references, so a symbol reachable only through the barrel and never
  called would still appear as dead (or test-only). This is the method that
  surfaced the two findings above.

- **Inter-sub-module imports do count.** `pure-fns-weeklyreport.js` imports
  `GAP_REPORT_UTILITY_TEXTS` directly from `pure-fns-gapreport.js` (not via
  the barrel). That counts as a real consumer, so `GAP_REPORT_UTILITY_TEXTS`
  is not dead even though no concatenated non-leaf file references it
  directly.

- **No dynamic imports.** `import(` was not found anywhere in the source
  tree, eliminating that analysis blind spot.

- **No source files were modified.** This report is informational only.
