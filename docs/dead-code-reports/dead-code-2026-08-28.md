## Methodology notes

- **Analysis date:** 2026-08-28.
- **Scope:** `src/js/*.js` (50 files) + `build.js` + `build-portable.js` +
  `build-config.js` + `smoke-tests.cjs` + `vite.config.js` +
  `deploy-portable.js` + `work-log.html` + `test/unit/*.mjs` +
  `test/calendar.Tests.ps1`.

- **Two-tier module architecture.** This codebase is *not* a uniform set of
  ES modules. Per `build-config.js` (`LEAF_MODULES`) and `build.js`:
  - 8 **leaf modules** (`app-constants.js`, `logger.js`, `date-labels.js`,
    `pure-fns.js` + its 4 `pure-fns-*.js` sub-modules) use real
    `export`/`import` syntax and are statically imported at the top of the
    generated `script.js`.
  - The remaining **42 files** (`00-config.js` through
    `25-rollingsummary.js`, `01b-migrate.js`, etc.) contain **zero** ES
    `export` statements — confirmed by grepping `^export (function|const|
    class|default)` across all of `src/js/*.js`, which matched only the 8
    leaf files. `build.js` concatenates these 42 files' raw text,
    alphabetically, directly into `script.js`'s top-level scope (see
    `buildJS()` in `build.js`). Their top-level `function`/`const`/`let`
    declarations are therefore not private to their source file — they are
    all visible to every other concatenated file at runtime, the same way
    they would be if hand-written in one giant file. There is no `import`
    statement connecting them because none is needed.
  - The skill's Step 2 anticipates this ("modules may concatenate directly
    without ES import syntax... note any module file listed by name"). Given
    that anticipation, and because a literal file-scoped reading of Step 3/
    Step 4 would produce hundreds of false "dead"/"unused" findings for
    functions that are genuinely called, just from a different physical
    file, this report applies the "never referenced by any other file"
    dead-export test to those 481 top-level declarations too (330 functions
    + 71 consts + 80 lets), using the whole search scope above rather than
    a same-file-only scope. This is a documented adaptation of Step 3/Step 4
    to this project's actual module boundary, not a deviation from the
    skill's intent (finding genuinely unreachable code).
  - `00-config.local.example.js` is excluded from both `build.js` and
    `build-portable.js` by design (`!f.endsWith('.example.js')`) — it's a
    dummy-values template a developer copies to a gitignored
    `00-config.local.js`, not dead code, and was excluded from the export/
    call-site inventory accordingly.
- **No default exports exist** anywhere in `src/js/` (`grep -n "export
  default"` returned nothing), so the default-export cross-check procedure
  in Step 3 had nothing to apply to.
- **Dynamic imports:** none found (`import(` does not appear in any JS
  source or build file) — every module is statically wired, so the
  "Possibly used" category is empty rather than unchecked.
- **Global/window exposure caveat handled, not flagged as dead:**
  `src/js/13-calendar.js` assigns a large `window.__wl = { … }` test-harness
  object (behind `?test=1`), `src/js/14-jira.js` assigns
  `window.__jiraToggle` (used by a dynamically-built `onchange` attribute
  string), and `src/js/15-notion.js` assigns `window._wlNotion`. Every
  symbol referenced inside those three assignments was independently
  confirmed to also have ordinary call-site usage elsewhere in the app —
  none is exposed *only* for the test harness or *only* for inline-HTML
  wiring, so none needed a "possibly used, don't remove" carve-out.
- **Word-boundary grep, not blind substring match:** all cross-referencing
  used `\bname\b` matching (not raw substring), so e.g. `log` does not
  false-positive against `logger` or `wlLog`. Ambiguous/short names (`load`,
  `save`, `render`, `dk`) were spot-checked individually to confirm the
  matches were real call sites rather than accidental substring hits inside
  longer identifiers the boundary regex might have mishandled.
- **False-negative risk, checked and mitigated:** the automated pass counts
  *any* word-boundary occurrence of a symbol's name, including mentions
  inside comments/JSDoc (e.g. "see `COLLAPSE_PREFIX` in
  `src/js/07-lifecycle.js`" — a real pattern in this codebase). A
  comment-only mention could in principle make a truly-dead function look
  "used." To guard against this, every declaration whose *only* non-own-file
  reference count was 1–2 was checked for whether it also had ≥2 references
  in its own file (i.e. real internal call sites, not just the declaration
  itself); and every genuinely file-local nested function (the 32-function
  population above) had its actual call site read directly, not just
  counted. No comment-only "usage" was found propping up an otherwise-dead
  symbol.
- **Test files searched:** all 26 files under `test/unit/*.mjs`, plus
  `test/calendar.Tests.ps1` (PowerShell — tests `server-helpers.ps1`/
  `start-server.ps1`, unrelated to `src/js/`, included for completeness but
  contributed no JS symbol matches).
