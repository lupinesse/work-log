**Process note — own the mistake, not just the fix.** The `v1.9.1` tag (created earlier this
week, at the user's request) was placed at `origin/main`'s HEAD *at the time*, on the reasoning
that `package.json` still read `1.9.1` and `CHANGELOG.md` still had a matching `## [1.9.1]`
section. That check was insufficient: two PRs (#306 CodeQL fix, #311 dead-CSS removal) had
landed on `main` under `## Unreleased` *after* the version bump, without bumping the version
again, so they shipped inside the `v1.9.1` tarball while the published release notes never
mentioned them. A same-day follow-up (`chore(release): consolidate Unreleased into v1.9.2`,
#329) correctly re-cut the boundary — this time tagging the exact release commit itself, not
"whatever HEAD happens to be." **Lesson for next time a tag is cut by hand:** verify no commits
landed under `## Unreleased` after the version bump, not just that the version string matches.

**Not yet fully clean:** even the `v1.9.2` cut needed a same-day correction (wrong date, one
missing entry — see Priority 3) found *after* the tag was already pushed and the GitHub Release
already published. `release.yml` renders release notes from `CHANGELOG.md` once, at tag-push
time — it does not update if `CHANGELOG.md` changes afterward, so the **published `v1.9.2`
release notes are currently missing the #326 entry and show the wrong date**, and will keep
doing so until someone edits the release by hand or re-cuts it. Not counted as a new checklist
regression (the `CHANGELOG.md`/tag process itself is what earned the promotion above), but real
and worth fixing — see Priority 3.
