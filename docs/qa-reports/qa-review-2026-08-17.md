## Priorities for this week

1. **`QA.md`'s "v1.9.0+ delta" test-count table is stale for a fifth consecutive review**, and
   `ARCHITECTURE.md`'s test-count line — refreshed just two days ago in #352 — is already stale
   too. `QA.md` still reads 647 unit / 99 suites / 1,215 total; actual is **659 / 102 / 1,259**.
   `ARCHITECTURE.md` reads 276 CI-script tests; actual is **280**. Both are honestly dated
   snapshots (`QA.md`'s section is explicitly labelled "as of 2026-08-13"), which is better
   practice than an undated claim, but the underlying number is still wrong today. Fold the
   refresh into the release-cut or PR-merge checklist so it doesn't need a dedicated QA-triggered
   fix every single week — this exact recommendation was also made last review.

2. **Fix the two unresolved 🔴 blocking findings from PR #355's own recorded review, both
   confirmed still present on `main` this review:**
   - `.github/scripts/impact-check.mjs` line 100 hardcodes `path.join('test', 'unit.mjs')` /
     `'test/unit.cjs'` as the only place it looks for unit-test coverage of a changed `src/js`
     file. Both paths were deleted by #355's own split, so `testFiles` silently collapses to just
     `smoke-tests.cjs` (`fs.existsSync` filters the dead paths out with no error). This script runs
     on every PR that touches `src/js/**` via `impact-check.yml` and posts a report — its "test
     coverage" column will now read `❌ not found` for essentially every `src/js` file, since most
     unit coverage lives only in the new `test/unit/*.test.mjs` files. Nothing catches this: there
     is no test file for `impact-check.mjs` anywhere in `.github/scripts/test/`. Fix: point
     `testFiles` at a glob over `test/unit/*.test.mjs`, and add a regression test.
   - `test/unit/_helpers.mjs`'s newly-exported `localDate()`/`localMs()` (lines 15, 19) have no
     JSDoc — see Regressions above.
   Both were flagged by name, with file/line citations, in the PR's own review 2h45m before merge.
   Treat "the project's own recorded review said REQUEST CHANGES and it merged anyway with zero
   follow-up commits" as a process failure independent of the two findings' individual severity —
   the whole point of Step 4 in CLAUDE.md's PR workflow is that this shouldn't happen.

3. **`04-render.js` remains the largest, least-split module** (892 non-blank lines) — fourth
   review running flagging this as the top unsplit file, still no split attempted. Unchanged from
   last review's Priority 1 remnant.

4. **Reconcile the Node-version story**: `.nvmrc`/`engines.node` were lowered from `24.15.0` to
   `22.22.1` this week (#353), verified only by checking each devDependency's own declared
   `engines.node` field — not by actually running the suite under Node 22. `ci.yml` and
   `.devcontainer/devcontainer.json` both still pin and test **Node 24 only**, so there is now a
   gap between the documented minimum-supported version and the only version anything actually
   verifies. The PR's own CHANGELOG entry already flags this ("no automated check that would catch
   a real Node-22 incompatibility today... pre-existing and out of scope") — it's honestly
   documented, but still open. Either add a Node-22 job to `ci.yml`, or raise the floor back to
   match what's actually tested.

5. **`(a) =>` single-letter-arrow-param density is unchanged for a sixth consecutive review**:
   `grep -rPo '\([a-z]\) =>' src/js/` still counts exactly **294**, same top files as every prior
   review (`14-jira.js` 22, `12-misc.js`/`11-timeflow.js` 20 each, `06a-hero.js` 19). No PR this
   week touched any of the top-density files enough to move the number. Lowest-effort fix: adopt a
   one-line ESLint rule (`id-length` with an allowlist, or a targeted `no-restricted-syntax`) so
   new code can't add to the pile even if the existing 294 aren't renamed in bulk.
