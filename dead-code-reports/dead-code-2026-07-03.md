## Methodology note — adapted for the concatenation model

The standard "named export never imported" analysis does not fit this
codebase as literally specified. `grep -rn "^export" src/js/` shows that only
6 of the 49 files in `src/js/` use ES `export`/`import` syntax at all:
`logger.js`, `pure-fns.js` (a barrel that re-exports the four modules below),
`pure-fns-format.js`, `pure-fns-validate.js`, `pure-fns-tasks.js`, and
`pure-fns-export.js`. These are real leaf ES modules, imported explicitly by
`build.js` into the generated `script.js` (`import { ... } from
'./src/js/pure-fns.js'`, `import { wlLog } from './src/js/logger.js'`) and by
each other (`pure-fns-export.js` and `pure-fns-tasks.js` both `import { dk }
from './pure-fns-format.js'`).

The other 43 files (`00-config.js` … `25-rollingsummary.js`) contain **zero**
`export` statements. Per `build.js`, they are read alphabetically and
concatenated as raw text into one `script.js` module (`build-portable.js`
does the same, wrapped in an IIFE, for the portable build). Because they end
up sharing one scope, a top-level `function`/`const`/`let`/`class` declared
in one file is callable by bare name from any other concatenated file with no
import statement — this is intentional architecture, not an oversight (see
`build.js`'s header comment and `LEAF_MODULES` in `build-config.js`).

Consequently:
- **Dead exports**: evaluated against the 6 real ES modules by checking every
  named export (including barrel re-exports in `pure-fns.js`) has a call site
  outside its own declaration.
- For the other 43 files, "export" doesn't apply literally, so — following
  the same adaptation used in this repo's 2026-06-23 and 2026-06-26 reports —
  every top-level `function`/`const`/`let`/`class` declaration was treated as
  the module's effective public surface and checked with a whole-word
  reference count across the full scope (definition line included). A count
  of 1 (only the definition, no calls anywhere) would mark it dead; this
  sweep found none.
- **Unused local functions** (Step 4): nested/closure-scoped `function name(…)`
  and `const name = (…) =>` declarations (indented, i.e. not top-level) were
  checked separately for a same-file call or a same-file callback-reference
  (e.g. `btn.addEventListener('click', closePanel)` — a bare reference with no
  `()` still counts as a use). All 32 candidates found have at least one such
  reference.
- **Dynamic imports**: `grep -rn "import(" src/js/*.js work-log.html` returned
  no matches anywhere in the tree, so this sweep has no "possibly used"
  candidates.
- **Default exports**: `grep -rn "export default" src/js/*.js build.js
  build-portable.js` returned no matches — no default exports exist in this
  codebase.

## Methodology notes
- Analysis date: 2026-07-03
- Scope for reference counting: `src/js/*.js` (49 files, including the
  build-excluded `00-config.local.example.js` template, which declares no
  symbols), `work-log.html`, `build.js`, `build-config.js`,
  `build-portable.js`, `smoke-tests.cjs`, `test/unit.mjs`
  (`test/calendar.Tests.ps1` is a Pester test for the PowerShell API server —
  out of scope, no JS symbols).
- Build entry points read per Step 2: `build.js` concatenates every
  `src/js/*.js` file alphabetically (excluding `LEAF_MODULES` and
  `*.example.js`) into `script.js`, with the six leaf ES modules imported at
  the top. `build-portable.js` performs the same concatenation, inlined into
  a single `<script>` IIFE for the portable build, stripping the leaf
  modules' `import`/`export` syntax so they merge into the same flat scope.
- Signal: whole-word reference count (identifier boundary, not substring) —
  a symbol whose only occurrence is its own definition (count = 1) is a dead
  candidate; none were found at this threshold. 477 top-level symbols and 32
  nested-function candidates were checked; the lowest reference count found
  was 2 (a definition plus exactly one call or reference), and every one of
  those was manually spot-checked to confirm the second occurrence is a real
  call site or callback reference, not a comment/string mention.
- Dynamic imports: none exist in this codebase, so no modules are marked
  "possibly used."
- Default exports: none exist in this codebase.
- Generated docs (`docs/*.html`), build artefacts (`script.js`, `styles.css`,
  `portable/`, `dist/`) are excluded from the reference-count scope — they are
  derived from source, not references to it.
